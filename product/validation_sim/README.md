# Симуляционная валидация механики тестирования

ТЗ §2: «команда предлагает собственную процедуру оценки своего решения, описывает её в сдаче и приводит результаты». ТЗ §3.4: «собственная процедура валидации решения и её результаты». ТЗ §6, критерий 2.

Пакет прогоняет 500 синтетических кандидатов с известным истинным грейдом через тест платформы и два эталона сравнения:

- **Единый набор** (`baseline.py`) — то, от чего предостерегает ТЗ §2: 3 вопроса, один ответ из трёх, общий для всех ключ (b, c, a), пересдача — тот же набор. Кабинет этим тестом не пользуется.
- **Банк без доборов** (`simulate.NewSystem`) — индивидуальный вариант из 12 вопросов по единому плану и оценка уровня по IRT, но без уверенности, доборов и накопления.
- **Платформа** (`adaptive.py`) — тест, который работает в кабинете: результат с уверенностью, дополнительные блоки у границы грейдов, накопление между попытками, вывод слабых тем по пилоту и осторожный порог. Две конфигурации банка: «Платформа» — `bank.live_view`, как в кабинете: 120 вопросов judge (три варианта «верно / неверно») и 96 со своим текстом (48 multi, 24 order, 24 numeric), на них ответ — одно число; «Платформа + форматы» — тот же тест на полном банке 288 семейств, не отложенное добавление форматов.

Показатели: точность, стабильность при пересдаче, разделяющая сила, устойчивость к уловкам и к утечке заданий.

Кабинет использует этот же код: `product/matching/assessment.py` собирает вариант и оценивает ответы функциями пакета (`form`, `irt`, `scoring`, `adaptive`) на банке в виде `bank.live_view`. Поэтому строка «Платформа» проверяет ровно то, что работает в продукте.

## Быстрый запуск

Команды выполняются из корня репозитория с активированным `.venv` или через `.\.venv\Scripts\python.exe`.

```powershell
python -m product.validation_sim.generate   # банк, 500 кандидатов и пилот (data/)
python -m product.validation_sim.run        # прогон, отчёт и графики (out/)
python -m pytest product/tests/test_validation_sim.py -q
```

Для графика нужен matplotlib (необязательная зависимость, в образ продукта не входит):

```powershell
python -m pip install matplotlib
python -m product.validation_sim.plot       # перерисовать по готовому out/results.json
```

Прогон занимает меньше минуты на обычном CPU, GPU не нужен. Кроме matplotlib для графика — только стандартная библиотека Python 3.10+.

## Файл кандидатов: как перенести в другую версию кода

Используйте `data/candidates.csv` (UTF-8 с BOM, открывается в Excel) или `data/candidates.json`. Файлы не ссылаются на таблицы проекта.

| Поле | Значение |
| --- | --- |
| `candidate_id` | `sim-0001` … `sim-0500`, стабильный ключ |
| `display_name`, `email` | Явно синтетические, домен `example.com` |
| `industry` | `it` |
| `specialization` | `backend`, `frontend`, `mobile`, `data`, `security` или `devops`, по 83–84 кандидата |
| `true_grade` | **Эталон**, истинный грейд. В продукте не показывать |
| `theta` | Истинный уровень на шкале `scale.py`, лежит внутри интервала `true_grade` |
| `declared_grade` | Грейд, на который кандидат заявился сам: 60% честно, 25% на ступень выше, 15% на ступень ниже |
| `team_role`, `work_format`, `stack` | Поля анкеты проекта. В CSV `stack` записан через `;` |
| `fsp_external_id` | Пусто: достижения ФСП в этом наборе не участвуют |

Распределение истинных грейдов: junior 35%, middle 30%, senior 22%, lead 13%.

Перенос в другую кодовую базу:

1. Скопируйте папку `validation_sim` целиком. Модули `scale`, `irt`, `bank`, `candidates`, `form`, `scoring`, `responders` и `simulate` работают без остального проекта; `bank.py` при этом построит банк без образцов текста.
2. `baseline.py` и проверка длины ответов берут тексты из `product.matching.stems`. Без него уберите блок `old` в `run.py`.
3. Если корневой пакет называется не `product`, замените префикс импортов `product.validation_sim` на свой.
4. Импорт кандидатов в кабинет: `email`, `specialization`, `declared_grade` (как `grade`), `team_role`, `work_format`, `stack` ложатся на поля профиля `PUT /api/candidate/profile`.

## Как устроен тест платформы

- **Семейство** — одна тема одной сложности с пятью равноценными вариантами-изоморфами. Варианты разные, а трудность у всех кандидатов одна (ТЗ §2).
- **План теста на грейд g:** 3 вопроса уровня g−1, 6 уровня g, 3 уровня g+1. Для junior и lead недостающие позиции добираются уровнем g.
- **Ключ хранится только на сервере.** У вариантов ответа одноразовые id, порядок перемешан, «буквы правильного ответа» нет.
- **Формат в кабинете.** Часть вопросов — judge: вопрос засчитан, только если верно оценены все три варианта (угадать — 1 из 8). Часть — одно число по своему тексту multi, order или numeric.
- **Пересдача** подбирает другие семейства. Частота показов выравнивается по всему банку.
- **Решение по уровню θ (IRT).** Принудительного понижения нет (ТЗ §2).

Двенадцать вопросов дают погрешность уровня около ±0.4 при ширине грейда 1.2, поэтому кандидат у самой границы грейдов иногда попадает в соседний грейд при любом тесте такой длины. Тест не пытается угадать грейд любой ценой: он сообщает, насколько уверен, и добирает информацию там, где она нужна.

1. **Результат с уверенностью.** Кроме грейда тест выдаёт вероятность того, что грейд верный, и положение внутри грейда (нижняя, средняя или верхняя треть). Статус «уверенно» — если вероятность не ниже порога из пилота, иначе «у границы».
2. **Дополнительные блоки у границы.** Если вероятность по спорной границе лежит между 15% и 85%, кандидат получает 6 вопросов сложности этой границы, не больше трёх блоков.
3. **Накопление.** Тест на грейд ниже или выше начинается с уже известного распределения уровня (две предыдущие попытки). Грейд ставят только тесты.
4. **Пилот.** На отдельной группе (seed 7, 1000 кандидатов, не пересекается с 500) выводятся темы, которые плохо различают кандидатов (корреляция с остальным тестом ниже 0.15): для банка кабинета 32 из 216. На той же группе выбирается порог «уверенно» — наименьший, при котором точность среди «уверенно» не ниже 93% + 0.5 п.п.: для банка кабинета 0.9.
5. **Осторожный порог.** Грейд присваивается, только если P(уровень ≥ граница) ≥ 60%. Завысить грейд хуже, чем занизить.

## Допущения и ограничения

- Ответы кандидатов смоделированы по IRT. «Настоящая» сложность вопроса отличается от записанной в банке (ошибка калибровки, sd 0.15), поэтому оценка не идеальна.
- Параметры вопросов (a, b) заданы, а не получены по пилоту на людях. В продукте их нужно уточнить по ответам первых кандидатов.
- Свой текст и числовой ключ есть у 48 multi, 24 order и 24 numeric (`own_texts`). У judge `variants[].text` пустой, кабинет показывает образец каталога. Длины вариантов ответа в каталоге выровнены: верный ответ самый длинный в 30% вопросов. Последние 3 из 12 семейств каждой пары повторяют темы (`sample.reused = true`) и в кабинет не входят. После правки `product/matching/stems.py` или `own_texts.py` пересоберите банк: `python -m product.validation_sim.generate`.
- Интервалы пересдачи по времени не моделируются.
- Точность среди «уверенно» опирается на 100–250 решений и колеблется между прогонами на ±2 п.п. Поэтому приводится среднее по 5 прогонам с разбросом.
- Утечка 50% банка означает утечку 720 вариантов вместе с ответами. Это крайний сценарий, и при нём защита слабеет. Поэтому банк нужно пополнять, а засвеченные варианты выводить из оборота.
